# 短剧多镜头视频提示词迭代设计

日期：2026-10-26

状态：已实施；v2 代码、schema、规则、Skill、文档与测试已同步

范围：Seedance 2.0 与 Seedance 2.5 同时升级（用户已确认）

## 1. 目标与交付边界

插件主要服务短剧。最终交付单位改为「一个待生成视频的一段完整提示词」，一个视频可以包含多个电影镜头。以完成一个独立、连续的叙事过程为优先，切换景别、正反打、插入特写本身不构成新视频的理由。超过目标模型生成时长等硬边界时，才在合理节点拆为多段，并交代衔接状态。

每段视频默认采用五个模块，名称和顺序固定：

1. 【生成目标】
2. 【参考素材职责】
3. 【主体与关系】
4. 【事件脚本】
5. 【保持一致】

只有剧本也必须产出提示词，并为每个角色、每个场景、每个关键道具各自建立至少一个参考图占位。占位不表示图片已经存在。Seedance 2.5 的每条事件描述必须具有明确的秒数区间；Seedance 2.0 默认按镜头顺序叙事，用户指定时间轴时也可显示秒数。

本轮不增加生产依赖，不改变 TypeScript、本地 MCP、Skill 创作的职责分工，不新增创作阶段。图片生成、素材上传、视频生成、编辑及延长任务、远端知识库修改不属于本轮实现。

## 2. 现状排查

以下为 2026-10-26 对当前工作区的静态检查结果。

| 方面 | 当前事实与定位 | 对新要求的影响 |
| --- | --- | --- |
| 阶段 | `README.md`、`docs/architecture.md` §9：解析 → 镜头规划 → 提示词，入口负责续跑与聚合 | 三阶段可以保留，职责需要升级 |
| 规划产物 | `schemas/shot_plan.schema.json` 只有 `scenes[].shots[]`，每个 shot 一组景别、机位、运镜和时长 | 缺少「待生成视频」层级，无法表达一个视频内多镜头 |
| 时长检查 | `server/src/tools/validate_stage_artifact.ts` 的 `validate_shot_plan_durations` 对每个 shot 使用模型 min/max，且要求整数秒 | 内部短镜头会被模型最小生成时长错误限制 |
| 拆分规则 | `rules/models/seedance-2.0.json` 偏向单主动作；2.5 仅允许同一连续镜头内多节拍 | 容易把切镜等同于另起一段生成，无法稳定保留完整过程 |
| PromptIR | `schemas/prompt_ir.schema.json` 顶层 `shots[]` 平铺；没有视频分组、实体素材绑定或结构化时间轴 | 需要明确的不兼容契约升级 |
| 渲染 | `server/src/tools/render_prompt.ts` 每 shot 单独输出，骨架是主体动作、对白、环境、镜头等九节 | 与五模块结构不一致 |
| 数字时间轴 | `skills/shot-prompting/SKILL.md`「数字时间段」只允许使用原文或用户已有数字，禁止自主切分时间轴 | 与 2.5 必须指定秒数直接冲突 |
| 实体与素材 | `script_analysis` 有角色、场景连续性，没有关键道具台账、稳定实体 ID、参考图槽位；入口没有素材输入契约 | 无法机械保证每类实体都有参考图占位 |
| 跨产物校验 | `read_run.ts` 检查产物自身及运行身份；`validate_prompt` 检查结构和模型规则 | 尚不能检查动作、台词、镜头的漏项、重复、错位 |
| 引用聚合 | `server/src/aggregate.ts` 将 PromptIR 的逐镜头引用展平 | 改为视频层级后需要同步遍历与归属 |
| 兼容性 | 架构 §11.2 将阶段 schema 视为冻结接口；现产物没有版本字段 | 旧 run 不能被默认为新契约，必须先识别版本 |

已具备、必须保留的能力：台词逐字保真、来源受约束的动作/情绪/声音、模型规则文件、确定性渲染、阶段人工编辑后重验、检索引用追踪和有限修复轮次。

## 3. 方案比较与推荐

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 仅在渲染时拼接现有 shots | 改动少；规划、最小时长、过程边界和来源覆盖仍然错误，渲染层承担创作判断 | 不采用 |
| 新增视频分组阶段 | 可以独立处理打包，但新增产物、状态、续跑入口及检索交接 | 当前规模下成本偏高 |
| 保留三阶段，规划产物增加视频层级 | 由规划阶段一起决策过程、时长和内部切镜；提示词阶段照计划撰写；校验层可验证视频总时长与镜头时间轴 | 推荐 |

用户已确认两个模型一起升级；上述内部实现方案为本次设计建议，尚未获得实施批准。

## 4. 概念和数据流

```text
script_analysis.json
  实体/参考素材槽位 + 原文单元 + 独立过程
    ↓ shot-planning
shot_plan.json
  scenes[] → clips[]（待生成视频）→ shots[]（视频内部镜头）
    ↓ shot-prompting
prompts.ir.json
  clips[]（每项对应一段完整提示词）
    ↓ 确定性校验、五模块渲染
prompts.<model>.md
  视频 v01：五模块，可包含多个切镜
  视频 v02：五模块，可包含多个切镜
```

继续保留现有七个运行文件名和三个 stage key。`shot_plan.json` 的名称表示其仍包含分镜计划，不再暗示逐镜头生成视频。

### 4.1 解析产物 v2

`script_analysis.json` 增加 `schema_version: 2`、`input_hashes.run_context`、顶层 `entities[]` 与 `reference_assets[]`，在每个剧本场次增加 `processes[]`。

- `entities[]`：`entity_id`、`entity_type: character|scene|prop`、`name`、`description`、`source_scene_ids[]`。场次中的同一实景可以引用同一个场景实体；外观、布景显著变化时使用独立参考槽位。不为无关布景碎物逐一建关键道具。
- 关键道具：参与动作、剧情证据、交接归属或连续性变化的对象。由解析阶段明确识别，并记录原文依据；无法确定的外观保留待补充，不编造设定。
- 现有动作、情绪、对白单元保留稳定 ID；增加各自涉及的 `entity_ids[]`。动作/情绪的文字仍来自原文及已允许的项目设定。
- `processes[]`：`process_id`、`goal`、`enter_state`、`exit_state`、`action_unit_ids[]`、`emotion_unit_ids[]`、`dialogue_unit_ids[]`、`entity_ids[]`。它是剧本中的一个完整过程，不是固定时长的视频。
- 每个应表现的原文单元必须归入一个过程；未被覆盖或缺少实体依据时返回明确问题，不静默丢弃。v2 的 `processes[]` 替代旧 `shot_group_suggestions[]`，不维护两套分组事实；镜头直接引用原文单元，不再依赖 `source_shot_group_ids`。
- 同一动作或情绪来源可以被多个内部镜头引用，也可以随同一过程跨视频；来源引用重复不等于事件重复。机械校验检查来源集合覆盖与有效性，是否把同一事件重新演了一遍由语义审查判断，不用 source ID 出现次数误拒合法切镜。

`reference_assets[]` 包含 `asset_id`、`media_type: image|video|audio`、`status: placeholder|provided`、`entity_ids[]`、`source?`、`adopt[]`、`exclude[]`。`source` 只保存用户已提供的本地路径或素材标识，不写凭据或虚构 URL；`placeholder` 不允许伪造 source。占位内容可进入提示词，不阻塞仅剧本输入。

入口可将用户提供的参考素材及其职责作为可选 `run.json.input_references[]` 保存，解析阶段据此创建资产条目；没有素材时创建占位。素材描述和映射未明确时记录待补充信息，不假装已经看过素材。运行级 `display_timeline?: boolean` 保存用户的秒数显示偏好；未指定时用模型默认，2.5 的强制规则不受 false 关闭。

### 4.2 规划产物 v2

`shot_plan.json` 增加 `schema_version: 2` 和 `input_hashes.script_analysis`，结构改为 `scenes[].clips[].shots[]`。内容指纹规则见 §9。

`clip` 字段：

- `clip_id`、`order`、`scene_id`、`process_id`。
- `goal`、`duration_sec`（整数）、`entity_ids[]`、`reference_asset_ids[]`。
- `continuity: { previous_clip_id, enter_state, exit_state }`。
- `split_reason`：首段为 `none`，后续分段为 `duration_limit|reference_limit|explicit_user_request`；自然进入新过程是新 process，而不是伪造拆分理由。
- `shots[]`：`shot_id`、`order`、`start_sec`、`end_sec`、现有景别/机位/运镜/转场、`purpose`、原文动作/情绪单元引用及镜头进入/离开状态。`purpose` 以短句说明切镜服务的既有剧情信息，不增加一套硬分类。
- `dialogue[]`：`dialogue_segment_id`、`dialogue_unit_id`、`speaker_id`、`start_offset`、`end_offset`、`start_sec`、`end_sec`。台词可跨越多个视觉镜头，内部切镜不重启、重复或截断台词。
- `audio`：`ambience`、`sfx`、`music` 三个数组，条目均为 `AudioCue: { cue_id, text, start_sec, end_sec, source_refs[] }`；来源项为 `{ kind: scene|unit|knowledge, id }`，必须引用原文场次/单元或已有知识引用。全程环境声/音乐显式用 0 到视频总长，门响等瞬时音效用具体动作发生的短区间。无来源时留空，提示词阶段沿用规划时间，不自行猜测音效在切镜前后的位置。

内部镜头使用正数秒区间，可以包含小数秒；模型最小生成时长不作用于内部镜头。视频总时长才使用模型允许的整数秒范围。时间比较使用 `0.001` 秒容差，属于插件计算约定。

视觉时间轴从 0 开始，相邻镜头首尾相接，最后一镜结束时等于视频总时长。叠化是转场描述，不通过重叠时段来表达。对白轨可以跨镜头，其区间必须位于视频内；是否同时说话由原文决定。

台词默认保持一个完整单元。确需跨视频时，只在自然句界切为片段；offset 使用 JavaScript UTF-16 字符串的半开区间，不能切断代理对。对同一原文单元，全部片段按序连续覆盖 `[0, text.length)`，无遗漏、重复或改字；每段的 text 由原文 slice 得到。是否为自然句界仍需语义审查，不用字符计数代替自然语速。

### 4.3 PromptIR v2

`prompts.ir.json` 增加 `schema_version: 2`、`input_hashes: { script_analysis, shot_plan }` 和必填 `display_timeline: boolean`，将顶层 `shots[]` 改为 `clips[]`。模型只在文档层指定，每段沿用同一目标模型。`display_timeline` 是模型强制规则与运行偏好的最终结果：2.5 必须为 true；2.0 未指定时为 false，用户要求时为 true。

每个 clip 包含：

- 身份和参数：`clip_id`、`scene_id`、`process_id`、`duration_sec`、`aspect_ratio`。
- `generation_goal`：本段要完成的事件及可观察结果。
- `reference_bindings[]`：`asset_id`、`media_type`、`entity_ids[]`、本段 `tag`、`status`、`adopt[]`、`exclude[]`。媒体类型显式保存以支持独立校验；有解析产物时再交叉核对，不从中文标签猜类型。
- `subjects_and_relations`：主体、数量、身份/服装、空间关系和道具归属。
- `shots[]`：沿用规划的镜头 ID、区间、镜头决策、来源引用，补足 `subject`、`action`、`emotion` 等有依据的画面文本。
- `dialogue[]`：从规划的对白轨取区间、segment/unit ID、说话人和 offsets，携带原文 slice 的 `text` 和现有可选语言/表达字段；全部片段拼接逐字还原上游台词。
- `setting`、`time`、`lighting`、`color`、`style`：保留现有信息和来源边界，供五模块内组装；不再另输出九节。`audio` 改为与规划一致的 AudioCue 三轨，source_refs 必须可解析，来源是否确实支持该声音仍需语义复核。
- `continuity`、`negative_prompt[]`、`knowledge_refs[]`。视频内引用保留 `shot_id`，视频共有引用可为 null，并增加 `clip_id`，避免同卡在多个镜头使用时丢失归属。

不另存第二份自由文本时间轴。秒数由结构化 shot/对白轨数据渲染，避免正文时间与规划数据互相漂移。

## 5. 短剧节奏与视频打包策略

规划顺序是「识别完整过程 → 估算对白和动作所需时间 → 设计内部切镜 → 检查视频上限 → 必要时拆段」，不使用固定五秒镜头起步，也不先逐镜头各生成一段再合并。

- 迅速进入当前冲突、信息或动作，不自动补长空镜、重复建立镜头、无信息停顿。
- 切镜必须服务已有的信息变化、反应、证据揭示或动作重点。短剧节奏是叙事密度和停留时机，不是固定数量的快切。
- 建议普通信息/反应镜头以约 1–3 秒作为初始估算；这是本插件的软规划建议，不是模型限制。对白长度、动作难度、悬念和情绪爆点需要时允许更长，不强行切碎。
- 完整过程在上限内默认保持一段视频，可以有正反打、特写和多个连续动作；多个互不相关的过程不为减少条数而硬塞一起。
- 超长过程在动作完成、短句结束、信息揭示等自然边界拆分，保留同一 process ID 和前后状态；最后短尾优先重新分配前后段，不增加原文没有的动作来凑最小时长。
- 一个完整过程本身短于模型最小时长时，可在原文已有动作或可见结束状态上合理停留；不新增剧情，也不强行拼接无关过程。若停留会明显破坏节奏或仍无法自然满足，报告时长冲突。
- 台词或不可拆动作明显无法容纳时，报告冲突并回到规划，不靠加速朗读、删台词、改剧情或超时来通过。
- 长台词需要时可按自然句界切成可追踪片段，片段按序拼接必须逐字还原原文；禁止任意切字。单个不可自然拆分的句子仍超限时报告需调整的来源单元。

## 6. 参考素材占位与编号

全运行以稳定 `asset_id` 关联同一素材；每段提示词按实际需要建立本地标签映射，如 `@图片1`、`@图片2`。标签与该段上传顺序一致；不同视频的数字可以不同，但资产身份不能漂移。正文所有标签必须能解析到该段的唯一绑定。

仅剧本输入时，每个角色、场景和关键道具分别生成至少一条 image 占位；同一实体跨视频复用同一 asset ID。每段视频只绑定自身涉及的实体，整集素材清单不全部塞入每段。

占位职责示例：

```text
【参考素材职责】
@图片1（待提供：角色A参考图）用于角色A的面貌与剧本已明确的服装；未明确的外观待补充，不采用图片背景。
@图片2（待提供：客厅场景参考图）用于客厅的空间布局、门窗和家具位置，不采用图中人物。
@图片3（待提供：信封参考图）用于关键道具信封的形状、颜色和封口状态，具体外观待补充，不采用图中手部和背景。
```

不能用一张群像占位替代多个角色各自的参考图。用户已明确给出的映射优先；没有参考视频/音频时不虚构视频/音频。参考职责必须同时说明采用内容和容易误带入而应排除的内容，避免自动复制示例里的木工、椅子等无关实体。

缺少实际图片时仍交付完整五模块草稿，同时在 `warnings.md` 标出素材待提供。若单段必须绑定的图片超过目标模型素材数上限，先尝试在合理过程边界拆分；同一不可拆场面仍超限时报告冲突，不漏掉实体、不冒充已就绪。

## 7. 五模块渲染与时间轴

| 模块 | 承载内容 |
| --- | --- |
| 生成目标 | 一个清楚的事件目标、起止结果和必要的整体视觉风格/环境口径 |
| 参考素材职责 | 本段逐素材的身份、采用范围、排除范围、占位状态 |
| 主体与关系 | 角色身份与数量、场景空间、关键道具归属和初始位置 |
| 事件脚本 | 顺序镜头、景别/机位/运镜、动作、原文台词、可观察情绪、必要声音；2.5 每条事件带秒数 |
| 保持一致 | 角色/场景/道具状态、空间方向、前后衔接及有依据的限制 |

每段视频在提示词正文外显示视频 ID、总时长、画幅和占位提示；可复制正文恰好五模块。无新增事件、台词、声音；无自动画质包/水印等无依据约束。保留现有中文枚举本地化和台词符号规则。

Seedance 2.5：每个视觉镜头输出 `0–2秒` 这样的数字区间；对白轨和声音 cue 使用独立数字区间，允许跨切镜。校验连续覆盖的是结构化视觉轨，不能把对白/声音与视觉轨重叠误判为错误。2.0 默认使用「镜头1／切至镜头2」「全程环境声」等顺序描述；内部仍保留结构化时间轴，用户开启秒数显示后各轨均显示区间。

示意（规划建议，非已经执行的新输出）：

```text
【事件脚本】
0–2秒：中景固定，木工检查木桌中央旧木椅的松动椅背。
2–5秒：切手部特写，木工沿接缝涂抹木胶。
5–8秒：切中近景，木工双手把椅背压回原位并固定。
8–10秒：切椅背特写，木工松开双手，椅背保持稳固。
```

这四个镜头属于一个十秒视频。用户示例里的动作仅用于解释分组，生产提示词必须来自实际剧本。

## 8. 校验与来源优先级

确定性校验至少覆盖：

1. 视频总时长在模型区间内、画幅合法；内部镜头正时长、不受模型最小时长限制。
2. 视觉区间从零连续覆盖到总时长，无倒序、负数、空洞、重叠和越界；对白/声音轨位于视频内，声音来源引用有效。
3. 原文单元、process、clip、shot、实体和素材 ID 存在且唯一，引用可解析；相同 shot 不得落入多个 clip。
4. 动作/情绪来源引用的集合覆盖应表现的单元，允许多镜头引用同一单元；台词片段区间精确覆盖原文一次，文字和说话人匹配上游。重复演出同一事件属于语义审查，不能单凭来源 ID 重复判定。
5. 每个仅剧本实体有独立 image 占位，本段每个必需实体有绑定；标签与绑定双向一致；placeholder 不含虚构文件。
6. 规划和 PromptIR 的视频、镜头顺序、时长、时间轴、参考 ID、台词分配一致，且保存的上游内容指纹匹配；人工只改动作文字或素材职责而保持 ID/时间不变，也必须让旧下游待重跑。
7. 2.5 时间轴渲染为必选，不能被知识卡或普通风格偏好关闭；五模块名称、顺序、数量准确。
8. 保留禁止工程参数、模型一致性、规则损坏报错、失败前不写渲染文件等现有保证；台词保真豁免仍然有效。

语义审查负责判断完整过程是否被无故切碎、快节奏是否合理、拆分点能否衔接、对白能否自然说完、角色和道具状态是否合理。ID/时间校验通过不代表视频模型会严格按秒或按镜头执行。

模型硬边界不可突破。内容与写作策略优先级：用户本轮要求 → 当前插件契约 → 项目知识 → 通用经验。旧知识卡中「一个镜头一段生成」「不自主写秒数」等冲突口径不得覆盖本轮规则。暂不自动写知识库；后续如需更新远端知识，单独预览、确认后执行。

## 9. 版本与续跑

对 `run.json`、`script_analysis.json`、`shot_plan.json`、`prompts.ir.json` 一起引入 `schema_version: 2`。旧文件缺失版本按 legacy v1 识别。

本轮选择明确拒绝 v1 续跑并提示从原始剧本创建 v2 run；不自动覆盖旧文件，不尝试把旧单镜头产物机械包装成合格的新视频。用户可以查阅旧输出；无需保留两套生成实现。`read_run` 必须在产物对账和任何写回之前识别不支持的版本并返回 `ARTIFACT_VERSION_UNSUPPORTED`，不把旧记录批量改为 failed。

新 run 版本混杂时停止，给出具体文件和版本。对 v2 的人工编辑，除 schema 重验，还要执行上游/下游对应关系校验；不匹配时把受影响下游视为待重跑，保留文件供检查。

内容指纹使用 Node.js 内置 SHA-256，对完整产物做递归对象键排序后的 JSON 编码计算；数组顺序保持。规划记录解析产物指纹，PromptIR 记录解析及规划指纹。键顺序调整不会造成失效；内容变化（包括动作文字、实体描述、素材采用/排除职责）会使下游失效。`validate_stage_artifact` 成功时返回 `content_hash`，供后续 Skill 复制到 `input_hashes`，不让 LLM 自行估算散列。参数与校验使用同一份已读取快照。

运行输入也参与失效检查：`hash_run_context` 仅取 `input_mode`、`project_id`、`target_model`、`aspect_ratio`、`input_references`、`display_timeline`，不包含 stages、warnings 等运行状态。初始化/读取工具返回 `run_context_hash`，解析产物记录到 `input_hashes.run_context`。`read_run` 将当前 run 与阶段产物一起核对；修改输入素材职责或显示偏好后，解析及所有下游待重跑，状态更新不会引发自我失效。
