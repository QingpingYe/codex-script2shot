## 1. 核验结论

### 1.1 已独立复现的事实

对 `run-20261027-105658` 的产物重新统计并重新执行当前插件校验，结果如下：

| 检查项 | 结果 |
| --- | --- |
| 产物规模 | 15 个 clip、49 个 shot、41 段对白、20 个 AudioCue |
| 含小数时间的 shot | 42 / 49 |
| 含小数时间的对白片段 | 37 / 41 |
| 含小数时间的 AudioCue | 5 / 20 |
| clip 总时长 | 全部为整数秒，平均 26 秒、中位数 27 秒 |
| shot 时长 | 平均 7.96 秒、中位数 7.70 秒、最长 12.5 秒 |
| 当前 `validate_stage_artifact(shot_planning)` | 通过 |
| 当前 `validate_prompt` | 通过 |
| 当前 `read_run` | 三个阶段的产物均有效 |

因此，复盘报告中的规模、时长和小数秒统计准确；“错误产物仍被当前插件判为合法”的判断也成立。

### 1.2 根因是否成立

成立，但责任边界需要写清楚：

1. **整数秒规则未统一，是真实的插件契约问题。**
   - `references/stage-conventions.md`、`docs/architecture.md`、`docs/model-rules-notes.md`
     和 `skills/shot-planning/SKILL.md` 当前明确允许内部 shot 使用小数秒。
   - `schemas/shot_plan.schema.json` 与 `schemas/prompt_ir.schema.json` 的
     `start_sec` / `end_sec` 均为 `number`。
   - `server/src/artifact_semantics.ts` 只强制 clip 时长为整数，shot、对白和
     AudioCue 只检查有限数、连续性和边界。
   - Seedance 2.5 官方提示词指南把时间戳定义为“以 1 秒为单位”，并写明 2.5 响应
     “整数秒的时间戳”。来源：
     <https://docs.volcengine.com/docs/ark/seedance-2-5-prompt-guide?lang=zh>，
     核验日期 2026-10-27。

2. **镜头过长主要是规划方法问题，不是插件自动切分错误。**
   - 插件没有自动分配镜头时长；产物中的 `11.1 / 20.8 / 12.5` 等时间由规划阶段写入。
   - 当前 `shot-planning` 已要求“按完整过程和对白/动作时间规划”，但没有给出可执行的
     时长估算方法。
   - 当前插件没有“长镜头例外说明”字段，也没有对明显长镜头做任何确定性拦截。

3. **当前规则不足以判断节奏质量，但足以修复契约缺口。**
   - 结构校验能保证连续、不越界、来源可回指，不能判断一个 7 秒镜头是否真的应该有 7 秒。
   - 因此本次不引入复杂的语义判断或自动剪辑器；只补整数秒硬约束、简单估算方法和一个
     可审计的长镜头例外字段。

### 1.3 对复盘报告的三处校正

1. 官方规则明确的是 Seedance 2.5 的提示词时间戳以整数秒为单位；Seedance 2.0
   不响应时间戳。把 2.0 的内部时间轴也统一为整数秒，是插件为一致性和可校验性增加的
   产品规则，不应写成两个模型相同的官方限制。

2. clip 接近模型上限本身不是缺陷。当前架构优先保留完整过程，一个 30 秒 clip 如果由
   合理节拍和多个短镜头组成，可以合法通过。本次不引入“clip 必须远离 max_sec”的规则，
   避免把模型上限误当节奏目标后反向制造新的机械切分。

3. `prompt_guidance.long_shot_staging_threshold_sec` 是提示词阶段的长镜头阶段化阈值，
   不是规划阶段的单镜最大时长。本次不会复用它来判定镜头时长，避免语义混用。

4. 复盘把“一镜表达一个主要动作或一个主要情绪”写成现有规范，但当前
   `skills/shot-planning/SKILL.md` 只明确“切镜必须服务信息变化、反应、证据揭示或
   动作重点”，没有逐镜只允许一个节拍的硬规则。本次补充“按节拍规划”和“按需组镜”，
   但不把一镜一节拍机械化成新的固定规则。

## 2. 目标与非目标

### 2.1 目标

1. 所有 clip、shot、对白和 AudioCue 的时间边界都使用整数秒。
2. 规划顺序改为“节拍 → 估算时长 → 组镜 → clip 累加 → 检查模型上限”，禁止先定
   clip 总时长再平均切镜。
3. 提供一个简单、可重复、可人工复核的镜头时长估算方法。
4. 对超过正常节奏的镜头要求明确例外说明，但不把创作判断伪装成确定性自动判断。
5. 不新增阶段、不新增 MCP 工具、不新增外部服务、不引入复杂 NLP 或自动切分器。

### 2.2 非目标

- 不做帧级剪辑控制。
- 不根据剧本原文自动生成镜头。
- 不保证模型一定严格按秒执行。
- 不把所有镜头压成固定时长或固定数量。
- 不因为 clip 接近模型上限而强制拆段。

## 3. 方案比较

### 方案 A：只改 Skill，不改校验器

在 `shot-planning` 中写整数秒和估算方法，由 Agent 自行遵守。

优点：改动最小，不触碰数据结构。  
缺点：无法阻止小数秒再次进入产物；复盘中的问题仍会通过结构校验。  
结论：不采用。

### 方案 B：只加校验器，不改规划方法

在语义校验中拒绝小数秒和超长镜头，但不告诉 Agent 如何估算。

优点：能阻断错误产物。  
缺点：Agent 仍可能先切 2–3 个长镜头，再被反复拒绝或机械凑整数，返工成本高。  
结论：不采用。

### 方案 C：整数秒硬约束 + 节拍估算 + 长镜头例外字段（推荐）

- 校验器负责确定性的时间不变量。
- Skill 负责可执行的节拍估算方法。
- 一个可选 `long_take_reason` 承载超长镜头的例外说明。

优点：补上根因，同时不改变三阶段架构和七文件产物边界。  
缺点：需要同步 schema、语义校验、fixtures、Skills、文档和测试。  
结论：推荐，作为本次迭代方案。

## 4. 推荐设计

### 4.1 全局整数秒不变量

以下字段全部必须是正整数或非负整数：

- `clip.duration_sec`
- `shot.start_sec` / `shot.end_sec`
- `dialogue.start_sec` / `dialogue.end_sec`
- `audio.<track>[].start_sec` / `end_sec`

统一不变量：

```text
第一镜 start_sec = 0
第 n 镜 start_sec = 第 n-1 镜 end_sec
最后一镜 end_sec = clip.duration_sec
每镜 end_sec > start_sec
所有秒数均为整数
```

实现口径：

- JSON Schema 继续保留 `type: number`，避免为了一个语义收紧升级 artifact 结构版本。
- `server/src/artifact_semantics.ts` 统一使用 `Number.isInteger`，对小数返回
  `TIMELINE_INVALID`，并保留 `clip_id` / `shot_id` 定位。
- 不自动四舍五入、不自动向下取整。发现小数时，回到 `shot-planning` 重做时间轴。
- PromptIR 校验也必须独立拒绝小数，不能只依赖上游 shot plan。
- 渲染工具继续复用 `validate_prompt_document`；校验不通过不写 Markdown。

### 4.2 镜头时长估算与 clip 分批顺序

估算过程可以使用临时小数，但不得写入任何产物。最终写入的 shot 时长是整数秒。

规划步骤固定为：

```text
原文单元
→ 拆成节拍
→ 估每个节拍的自然时长
→ 合并为镜头并把每镜向上取整为整数秒
→ 得到整个过程的镜头序列（此时还不决定 clip 边界）
→ 在自然边界上把镜头序列分批装入 clip
   同时检查模型 min_sec、max_sec 和参考素材上限
→ 每个 clip 内从 0 开始重新累计 shot 时间
→ clip.duration_sec = 本批 shot 整数时长之和
→ 检查对白切分、AudioCue 和前后状态
```

“节拍”定义为最小的新信息或状态变化：一句对白、一次反应、一个动作变化、一次插入
信息或一个必要的可见停留。一个镜头可以包含多个同机位、同连续动作的节拍；出现新的
信息点、反应或空间关系时需要切镜。

默认估算表：

| 节拍类型 | 初始估算 | 规则 |
| --- | --- | --- |
| 中文对白 | 约 3.5–4 字/秒 | 普通对白取 3.5–4；强调、哭腔、停顿取 3；向上取整 |
| 英文对白 | 约 2.5–3 词/秒 | 向上取整；专有名词和慢速表演可降速 |
| 反应 / 插入 | 1–2 秒 | 只看一个表情、手部、道具或证据信息 |
| 简单动作 | 2–3 秒 | 一个起止明确的动作 |
| 复合动作 | 4–6 秒 | 动作有多个阶段但仍在一个镜头内完成 |
| 可见停留 / 转场 | 1 秒 | 只在原文有状态变化、空间关系或连续性需要时使用 |

合并规则：

- 同一镜头内对白与动作重叠时取 `max(dialogue, action)`，不把两条时间相加。
- 先后发生的节拍才相加；加总后每镜向上取整一次。
- 反应和插入镜头不得为了填满 clip 而拉长。
- 对白台词必须完整覆盖，宁可增加一个听者反应或可见停留，也不压缩台词时间。
- 允许项目知识或用户明确给出的语速覆盖默认值；不得用一个全局固定镜头数覆盖原文节拍。

### 4.3 长镜头例外

在 `shot` 上增加一个可选字段：

```json
{
  "long_take_reason": "连续跟拍角色从门口走到床边，中间没有新信息点，需要保持同一空间连续"
}
```

规则：

- `shot` 时长不超过 6 秒时，字段可以省略。
- `shot` 时长大于 6 秒时，`long_take_reason` 必须是非空字符串。
- `shot-planning` 和 PromptIR 两个语义校验都要检查该条件。
- PromptIR 的 shot 必须原样复制规划中的 `long_take_reason`；下游修改该字段视为
  与上游不一致。
- 7–12 秒允许作为例外；超过 12 秒时，规划阶段应先检查是否能按动作完成、短句结束
  或信息揭示拆镜。若确实必须保留连续长镜头，仍可通过 `long_take_reason` 放行，
  但不自动强制拆段。
- `long_take_reason` 是内部规划字段，不要求出现在最终 Markdown 正文。

这个字段只解决“明显长镜头无说明”的问题，不把语义判断写成硬编码。长镜头是否有
创作必要，最终仍由规划和人工审查判断。

### 4.4 clip 分批与打包规则

- 先完成整个过程的镜头序列，再决定 clip 边界。不要把所有镜头先累加成一个“理论
  clip”，最后才检查模型上限。
- clip 边界必须落在镜头边界上，并优先选择动作完成、短句结束、反应结束或信息揭示等
  自然节点。若必须在一镜内部切段，先把该镜头拆成两个镜头。
- 对每个候选 clip，同时检查：
  - 总时长为整数秒；
  - 总时长不小于模型 `min_sec`；
  - 总时长不大于模型 `max_sec`；
  - 本段参考素材数量不超过模型上限；
  - 对白可以在自然句界处分配到前后 clip，offset 覆盖不重复、不漏字；
  - 前后 clip 能写明 `previous_clip_id`、进入状态和离开状态。
- 分批时优先选择“不超过 max 的最长自然前缀”，但仍需保证剩余部分为 0 或不少于
  `min_sec`。如果最长前缀会留下小于 `min_sec` 的尾段，应向前回退到更早的自然边界。
- 示例：一个 32 秒过程、`max_sec=30`、`min_sec=4` 时，不应机械切成 30+2；
  应选择例如 16+16 或 28+4 的自然边界。一个 18 秒过程在 2.0 下应选择
  9+9 或其他满足 4–15 秒的自然边界，而不是 15+3。
- 若回退后仍无法同时满足时长、素材和对白完整性，报告规划冲突，不静默删除素材、
  改台词或新增剧情。
- clip 时长等于本批最后一个 shot 的 `end_sec`，也等于本批所有 shot 时长之和。
- 接近上限但所有约束成立时允许保留，不因接近上限本身触发拆分。
- 低于模型 `min_sec` 时，只能用原文已有的动作、反应或可见停留补足；不得新增剧情或
  强行拼接无关过程。

### 4.5 对白与声音

- 对白片段和 AudioCue 使用同一整数秒时钟。
- 对白可以跨 shot，但起止边界必须是整数秒。
- 全程环境声/音乐自然覆盖 `0` 到 clip 总时长。
- 瞬时音效应落在整数秒边界内，不能以小数制造虚假精度。

## 6. 验收标准

### 6.1 确定性校验

1. shot、对白或 AudioCue 任一时间字段为小数时返回 `TIMELINE_INVALID`。
2. 整数秒时间轴连续覆盖 `0..clip.duration_sec` 时通过。
3. 7 秒 shot 缺少 `long_take_reason` 时失败；提供非空说明时通过。
4. 6 秒 shot 不需要 `long_take_reason`。
5. PromptIR 中 shot、对白或 AudioCue 出现小数时失败。
6. PromptIR 的 `long_take_reason` 与 shot plan 不一致时失败。
7. `render_prompt` 遇到小数 PromptIR 时不创建或覆盖输出文件。
8. 现有 schema、语义、渲染和 MCP 握手测试全部通过。

9. 一个 32 秒过程在 2.5（`max_sec=30`）下不得被切成 30+2；切分后的每个 clip 都必须落在 4–30 秒。
10. 一个 18 秒过程在 2.0（`max_sec=15`）下不得被切成 15+3；应选择满足 4–15 秒的自然切分。
11. 同一过程的第二个 clip 必须从 `0` 重新累计 shot 时间，并通过 `previous_clip_id` 和前后状态承接。
12. 参考素材数量超限时，应先调整自然 clip 边界；无法调整时返回明确错误，不删除素材。

### 6.2 规划质量

1. 不得出现“先定 clip 时长，再按镜头数平均分配”的产物。
2. 普通对白、反应、插入镜头以 1–4 秒为主。
3. 简单动作以 2–3 秒为主，复合动作以 4–6 秒为主。
4. 超过 6 秒的镜头逐条有可核对的长镜头说明。
5. 30 秒 clip 可以由多个合理短镜头组成；不要求固定镜头数。
6. 对白逐字覆盖原文，镜头切分不造成台词改字、漏字或重复。

7. 过程跨多个 clip 时，每个 clip 均为整数秒且处于模型 `min_sec..max_sec`。
8. clip 切分优先落在自然节点，不把模型上限当成固定目标。
9. 对白跨 clip 时在自然句界切分，offset 拼接后逐字还原原文。

### 6.3 验证命令

实现阶段至少运行：

```text
cd server
npm run typecheck
npm test
```

并用实际 run 重新执行：

```text
validate_stage_artifact(shot_planning)
validate_prompt
render_prompt
```

## 7. 迁移与重跑

- artifact `schema_version` 保持 `2`；这是对 v2 时间语义的收紧，不新增产物形态。
- 旧 run 中已经含小数秒的 shot plan / PromptIR 会被新校验拒绝，这是预期行为。
- 受影响的 run 从 `shot_planning` 阶段重跑，不自动改写旧产物，也不做数值四舍五入。
- 续跑仍遵守既有上游指纹和 `read_run` 规则。
- 发布版本递增为 `0.2.2`，实现完成后同步 `plugin.json` 与 `server/package.json` 的版本。

## 8. 风险与边界

- 估算表是创作初值，不是模型硬限制；项目知识或用户明确要求可以调整语速和动作时长。
- 整数秒只保证时间表达一致，不保证模型生成时严格按秒执行。
- 6 秒阈值只能拦截“没有说明的明显长镜头”，不能判断所有节奏问题。
- 不使用“平均镜头数”“固定每镜秒数”等机械规则，避免把已发现的问题换一种形式重现。

## 9. 推荐结论

采用方案 C：先修整数秒契约，再把镜头时长估算写进规划 Skill，最后用一个可选的
`long_take_reason` 承载合理例外。该方案解决本轮的 hard bug 和主要返工原因，同时保持
三阶段架构、七文件产物和现有工具边界不变。
